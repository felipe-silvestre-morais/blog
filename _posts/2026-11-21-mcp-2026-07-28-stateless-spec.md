It has been a while since I last wrote here, and in the meantime the protocol I have written about the most quietly had its biggest rewrite yet.

On 28 July 2026 the **Model Context Protocol** shipped a new version of its specification, `2026-07-28`. The maintainers themselves described the changes as the most substantial since authorization was added. And most developers I talk to have not really looked at it, because "a new protocol version" sounds like the kind of thing you will deal with later.

Later is now a few months ago. So here is my attempt at a plain-language walk through what changed, why it changed, and what you should actually do about it. If you have only ever *used* MCP servers (installed one, pasted a config, moved on), you can still follow along. If you *build* MCP servers, this one is more or less mandatory reading.

A quick note on sources before we start: everything technical below comes from the official [changelog](https://modelcontextprotocol.io/specification/2026-07-28/changelog) and the [MCP blog post](https://blog.modelcontextprotocol.io/posts/2026-07-28/) announcing the release. Where third-party write-ups disagree with them, I went with the official ones.

---

## The One-Sentence Version

MCP used to be a **conversation** between a client and a server. Now it is a series of **independent requests**.

That is the whole story. Almost everything else in the release is a consequence of it.

---

## Quick Refresher: How MCP Worked Until Now

In the old model, every connection started with a handshake. The client said "hi, here is my protocol version and what I can do", the server said "hi, here is mine", and the client confirmed. After that, the server gave the connection an identity (in the HTTP transport, an `Mcp-Session-Id` header) and both sides remembered each other for the life of the connection.

Think of it like a phone call. You dial, you say hello, you establish who you are, and then you talk. If the line drops, you call back and start over with "hello, it's me again".

That model is fine on a laptop, where your agent launches your MCP server as a local process and they chat happily for the whole session. It gets painful when you try to run an MCP server like a normal web service:

- **Load balancing is awkward.** If a session lives in one server instance's memory, the next request has to land on *that same instance*. Either you configure "sticky sessions" or you build a shared session store. Both are things you would rather not have.
- **Dropped connections lose state.** The line drops, the session is gone, and the client has to re-initialize.
- **Serverless does not fit.** Functions that spin up per request and vanish do not have anywhere to keep a session.

The maintainers say moving away from sessions was one of the most requested changes from people running MCP servers in production. I believe it, because these are exactly the problems you hit the moment you leave your laptop.

---

## The Big Change: No More Sessions, No More Handshake

Here is what the new spec removes:

- The `initialize` request and the `notifications/initialized` follow-up are **gone**.
- The `Mcp-Session-Id` header is **gone** from the Streamable HTTP transport.
- Because there is no session, `tools/list`, `resources/list` and `prompts/list` are no longer allowed to vary from connection to connection.

So how does a server know who it is talking to? **Every request now carries its own context.** Client identity, capabilities and protocol version travel in the request's `_meta` field each time. Here is the example from the official blog post, trimmed slightly:

```http
POST /mcp HTTP/1.1
MCP-Protocol-Version: 2026-07-28
Mcp-Method: tools/call
Mcp-Name: search

{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "tools/call",
  "params": {
    "name": "search",
    "arguments": { "q": "otters" },
    "_meta": {
      "io.modelcontextprotocol/clientInfo": { "name": "my-app", "version": "1.0" }
    }
  }
}
```

If you want the phone analogy to survive: this is no longer a phone call, it is **sending letters**. Every letter has the return address and everything the recipient needs to understand it written on the envelope. It does not matter which postal worker picks it up or which desk it lands on.

Notice the new `Mcp-Method` and `Mcp-Name` headers too. Streamable HTTP POST requests now require them, which means a load balancer or API gateway can route or filter on "this is a `tools/call` for the tool called `search`" **without parsing the JSON body**. That is a small detail with a big operational payoff.

### "But How Does a Client Discover What a Server Supports?"

With the handshake gone, there is a new method, **`server/discover`**. Servers must implement it, and it returns the protocol versions, capabilities and identity of the server. Clients *may* call it up front to pick a version, but they do not have to. If a client sends a protocol version the server does not support, the server answers with an `UnsupportedProtocolVersion` error and the client can adjust.

### "What About Things That Genuinely Need State?"

This is the part I found most interesting, because "stateless" can sound like "you cannot build anything stateful any more". That is not what the maintainers are saying. The official blog is explicit that dropping the protocol-level session does not force your *application* to be stateless.

If your server needs to remember something, it mints an **explicit handle** from a tool, for example a `cart_id` or a `browser_session_id`, and the model passes it back as an ordinary tool argument on later calls. State moves from being *hidden in the transport* to being *visible in the conversation*. The model can see it, thread it through, and you can inspect it in logs.

I actually think this is the better design. Hidden session state is the thing that makes agent behaviour hard to reason about. A handle in the arguments is just data.

## What Else Changed (The Parts You Will Trip Over)

Here is the rest of the changelog in plain English, in rough order of how likely you are to care.

### Subscriptions: One Stream Instead of a Pile of Endpoints

Servers used to push "hey, my list of tools changed" notifications over a separate HTTP GET stream, with `resources/subscribe` and `resources/unsubscribe` on top. That is replaced by a single method, `subscriptions/listen`: one long-lived response stream where the client opts in to exactly the notification types it wants (tools changed, prompts changed, resources changed, specific resource subscriptions).

Related cleanup: `ping`, `logging/setLevel` and `notifications/roots/list_changed` are removed. If you want server logs for a request, you ask for a level on that request through `_meta`.

### Servers Asking the Client for Things: "Multi Round-Trip Requests"

In the old protocol, a server in the middle of a tool call could send its *own* request back to the client: "please ask the user this question" (elicitation), "please run this prompt through your model" (sampling), "what directories are you working in?" (roots). That only works if there is a long-lived two-way connection, which is exactly what we just removed.

The replacement is a pattern called **Multi Round-Trip Requests**. Instead of making a callback, the server simply answers with a result whose `resultType` is `"input_required"`, plus a list of what it needs. The client gets the answers and **retries the original request** with the answers attached as `inputResponses`.

Back to the letters: instead of the recipient phoning you mid-reading with a question, they write back "I need your account number to continue", and you re-send your original letter with the number stapled to it.

A knock-on change: **every result now has a `resultType`**, either `"complete"` or `"input_required"`. Results from older servers that omit it should be treated as `"complete"`.

### Tasks Became an Extension

Long-running work (the "start this, I will check back" pattern) used to be experimental and built into the core. It now lives in an extension called `io.modelcontextprotocol/tasks`. The blocking `tasks/result` call is replaced by polling with `tasks/get`, there is a new `tasks/update` for the client to send input into a running task, and `tasks/list` is gone. Servers can also hand back a task handle without the client having asked for task support first.

That fits the stateless philosophy: a task is just an ID you poll, not a connection you keep open.

### Caching Hints Are Now Required on List Results

Results from `tools/list`, `prompts/list`, `resources/list`, `resources/read` and `resources/templates/list` must now include `ttlMs` (how long the result stays fresh, in milliseconds) and `cacheScope` (`"public"` or `"private"`). If you ever put a CDN or a proxy in front of an MCP server, you will appreciate this. The spec also says servers *should* return `tools/list` in a deterministic order, which sounds boring until your prompt cache keeps getting invalidated because tools shuffled around.

### JSON Schema Got Real

`inputSchema` and `outputSchema` can now use any keyword from **JSON Schema 2020-12**, and `structuredContent` can be any JSON value rather than just an object. If you ever fought the old, narrower schema support to describe a tool properly, this is a quality-of-life win.

### Smaller Things Worth Knowing

- OpenTelemetry trace keys (`traceparent`, `tracestate`, `baggage`) are now documented for `_meta`, so you can trace one request across agent, MCP server and whatever the server calls.
- Resource-not-found changed from error code `-32002` to `-32602` (Invalid Params), and a few spec-defined error codes were renumbered into a reserved `-32020` to `-32099` range. If your client matches on numeric codes, check them.
- SSE **resumability is removed**. If a response stream breaks, the in-flight request is lost and the client re-issues it as a *new* request with a new ID. So make your tools safe to retry.

## The Authorization Changes (Short, but Important)

I wrote about [MCP tunnels]({% post_url 2026-05-26-mcp-tunnel-security %}) earlier this year because credentials and cloud agents make me nervous. The authorization changes in this release are in the same spirit, and they are mostly about closing specific, well-understood holes:

- **Issuer checking.** Authorization servers should include an `iss` parameter in their responses (RFC 9207), and clients **must** validate it before redeeming the authorization code. This defends against "mix-up" attacks, where a malicious server tricks a client into sending a code to the wrong place.
- **Credentials bound to their issuer.** A client must store its credentials keyed by the authorization server that issued them, never reuse them with a different one, and re-register if the server changes.
- **Dynamic Client Registration is deprecated.** The new preferred mechanism is **Client ID Metadata Documents**. DCR still works for authorization servers that do not support the new approach, but its days are numbered.
- **`application_type` on registration.** Desktop and CLI clients need to say what they are so authorization servers stop rejecting `localhost` redirect URLs.

There is also an extension for enterprise-managed authorization, where an IT admin approves access through the company identity provider once and users connect automatically. The details of that live outside the core spec.

## What Got Deprecated

The release also introduces a formal **feature lifecycle**: features are *Active*, *Deprecated* or *Removed*, and anything deprecated stays in the spec for **at least 12 months**. Under that policy:

| Deprecated | Suggested replacement |
|---|---|
| **Roots** | Pass directories or files through tool parameters, resource URIs or server configuration |
| **Sampling** | Call the LLM provider's API directly |
| **Logging** | Log to stderr (stdio) or use OpenTelemetry |
| **HTTP+SSE transport** | Streamable HTTP |
| **Dynamic Client Registration** | Client ID Metadata Documents |

Deprecated means "still works, do not build new things on it". It does not mean everything breaks tomorrow. But Sampling in particular is a significant one, because "let the server borrow the client's model" was one of the more distinctive ideas in MCP. The recommended path now is for the server to use its own model access.

## So What Should You Actually Do?

It depends which side of the protocol you are on.

**If you only use MCP servers** (Claude Code, Cursor, desktop apps): almost nothing. Your tools will update, and your config files keep working. You may notice remote servers getting more reliable and easier to host, and a gradual shift towards interactive UIs inside the chat through the MCP Apps extension.

**If you build MCP servers:**

1. **Search your code for session assumptions.** Anything that reads `Mcp-Session-Id`, stores data keyed by connection, or depends on `initialize` having run needs rethinking.
2. **Replace hidden state with explicit handles** that your tools return and accept.
3. **Implement `server/discover`** and start sending `serverInfo` in result metadata.
4. **Add `ttlMs` and `cacheScope`** to your list results, and return tool lists in a stable order.
5. **Make tools idempotent**, because a dropped stream now means a fresh retry, not a resumed one.
6. **Stop adopting Roots, Sampling and Logging**, and plan a migration if you rely on them.
7. **Check the SDK migration notes.** TypeScript, Python, Go and C# SDKs support the new version, and Rust was reported to be in beta at launch.

**If you build MCP clients or agents:** put protocol version, capabilities and client info in `_meta` on every request, handle `input_required` results by retrying with `inputResponses`, validate the `iss` parameter, and key stored OAuth credentials by issuer.

If you are starting a *new* server today, build it on the new spec from day one. There is no good reason to write fresh code against a design that is already on the deprecation path.

## The Honest Caveats

I do not want to oversell this, so here are the rough edges I noticed while reading:

- **There is real migration cost.** The maintainers say so themselves, especially for anyone who relied on session identifiers. This is not a "bump the version number" release.
- **Parts of the changelog are terse.** It names `tasks/get` and `tasks/update` but leaves the details to separate proposals, and it does not say what a client should do when an older server omits the new required caching fields. I would read the linked SEPs before building anything serious on Tasks.
- **Third-party summaries disagree with the official ones.** Several pre-release articles describe things as "proposed" that landed differently in the final version (for example, what exactly replaces Dynamic Client Registration, or whether OAuth 2.1 is mandated). I would trust the changelog and the official blog over anything written about the release candidate.
- **Client support is a rollout, not a switch.** Anthropic's announcement says support is being rolled out across Claude products, without dates. Do not assume every client you use already speaks the new version, and check before you migrate a server that depends on a specific one.

## Final Thoughts

I like this direction a lot. The original MCP design assumed a friendly, long-lived conversation between two programs on the same machine. That was a reasonable thing to design for in the beginning, but it is not how people deploy software, and it is definitely not how cloud agents and remote servers behave. A protocol built on independent, self-describing requests is one you can put behind a load balancer, a CDN, an API gateway, a serverless platform and an audit log, all of which are boring tools that serious systems already know how to operate.

There is also a quiet theme worth noticing across the whole release: **make the invisible visible.** Session state becomes explicit handles. Server callbacks become ordinary request/response rounds. Per-request metadata replaces assumptions about "whoever connected earlier". That is good for scaling, but it is also good for the thing I keep coming back to on this blog, which is being able to see and control what your agents are doing.

If you build on MCP, pick one of your servers this week, read the changelog next to your code, and write down every place you rely on a session. That list is your migration plan.
